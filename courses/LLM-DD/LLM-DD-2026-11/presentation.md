# Qdrant: поиск по документам с фильтрацией по метаданным

## Цели

После занятия вы сможете:

1. Создать коллекцию Qdrant с payload
2. Ограничить выдачу фильтром по метаданным
3. Получить ответ LLM только из найденного контекста

## Смысл занятия

Не отдавать в RAG похожий, но неуместный документ: чужой отдел, устаревшая версия, другой тип инструкции.

## Теория 1. Вектор, payload и коллекция

Точка в Qdrant состоит из трех частей:

- идентификатор
- вектор - числовое представление текста
- payload - метаданные и исходный текст

Коллекция задает размер вектора и метрику расстояния. Для смыслового поиска обычно берут косинус.

Поиск идет по вектору. Фильтрация и показ пользователю идут по payload. Если в payload нет поля, по нему нельзя надежно отфильтровать выдачу.

## Теория 2. Поиск по сходству

Запрос тоже превращается в вектор той же моделью, которой кодировали документы.

Qdrant возвращает ближайшие точки по метрике коллекции. Высокий score означает близость формулировок, а не разрешенность документа для этого запроса.

Типичный сбой RAG: слова совпали, смысл соседний, но документ из другого процесса. Пример: «оформить возврат» находит и возврат товара, и возврат дней отпуска.

На этом шаге нет понимания отдела, года или статуса документа. Есть только геометрия векторов.

## Теория 3. Метаданные документа

Метаданные - поля, которые вы записываете в payload при индексации. Их нельзя надежно восстановить из эмбеддинга после факта.

Минимальный набор для корпоративной базы:

- `department` - какой отдел владеет документом
- `doc_type` - политика, инструкция, FAQ
- `year` - версия или год действия
- `title` и `text` - что показать человеку и модели

Поля должны повторять реальные ограничения продукта: «ищи только в актуальных правилах магазина», а не свободные теги автора.

Индексируйте те поля, по которым будет фильтр. Индекс payload лучше создать до загрузки точек.

## Теория 4. Условия фильтрации

Фильтр применяется к payload до или вместе с поиском по вектору. В выдачу попадают только точки, которые одновременно близки по смыслу и проходят условие.

Базовые конструкции:

- `must` - все условия обязательны (логическое И)
- `should` - достаточно одного (логическое ИЛИ)
- `must_not` - исключить значения
- `MatchValue` - точное совпадение строки
- `Range` - диапазон для числа, например год

Пример: `department = shop` и `doc_type = returns` и `year >= 2025`. Без этих условий векторный поиск может вернуть HR-документ про отпуск.

## Теория 5. Ошибки проектирования payload

Частые ошибки:

- фильтровать по полю, которого нет в payload
- класть год и статус только в текст, а не в отдельное поле
- смешивать типы: `"2025"` как строка и `2025` как число
- не создать индекс и удивиться медленному фильтру на большой коллекции
- один чанк без метаданных родителя: фильтр по документу перестает работать
- слишком широкие теги вроде `doc_type = other`

Проверка: один и тот же запрос с фильтром и без. Если топ не изменился, либо корпус слишком маленький, либо фильтр не отсекает ничего осмысленного.

## Теория 6. Контекст для LLM

RAG здесь линейный: запрос, поиск, сборка контекста, один вызов модели. Модель не ходит в Qdrant сама.

Локальный контур занятия:

- Ollama на `http://localhost:11434/v1`
- модель `llama3.2:3b`
- официальный OpenAI SDK, меняется только `base_url`

Правило промпта: отвечать только по переданным фрагментам. Если в контекст попал HR-отпуск, маленькая модель честно «поможет» с отпуском. Фильтр payload чинит это до генерации, а не после.

## Практика

План (совпадает с `practice.md` и `code/`):

1. Поднять Qdrant и создать коллекцию
2. Загрузить небольшую коллекцию документов
3. Выполнить обычный поиск
4. Добавить фильтры по метаданным
5. Сравнить выдачу запросов
6. Собрать ответ LLM из найденного контекста
